## [0.9.14-alpha] - 2026-08-14
- **admin_mods addresses modules, their access level and the pages they attach to by lid — and the render harness stops hiding how much of a diff it is not showing you.** Four screens of six. The harness change is the more useful half of this entry, because it is about how the other conversions were reviewed.
  - **`render_diff.sh` piped each diff through `head -12` and stopped, silently.** A 10-line diff and a 140-line diff looked identical on screen. This release's two files carry **70 changed lines each**, and the twelve shown were all `<option>` values — the `?mod_nid=` → `?mod_lid=` link substitutions, which are the actual subject of the change, began at line 117 and were never printed. "Every changed line was inspected" is a claim several recent entries make, and for those it was true only because their diffs happened to fit. It now prints `… N more line(s) hidden; M changed line(s) in total`, the exact `diff` command to see the rest, and honours `DIFF_LINES=0` to print everything. **A gate that truncates its own evidence without saying so is the same defect as a sort that never sorts** (0.9.13) or a rule that fires on correct input (0.9.6) — the output looks like the whole story.
  - **The conversion itself covers three controls, not one.** The module's level is a single-choice picker and the pages it serves are a multi-select, so this screen needed both a scalar and a list resolver: [`lunaModel::nid_from_lid()`](luna/luna.classes/luna.model.class.php) is added as the singular of `nids_from_lids()`, returning `0` rather than `false` so the result can go straight to the guards, which take an int. `user_can_access_level()` receives the resolved nid exactly as before, and the `intval()` that used to wrap the raw POST value is gone from both submit paths.
  - **L17 is the strongest assertion in the lid suite so far, and it is strong because of how `submit_modify()` is built.** It unlinks *every* page and level from the module and then re-links whatever the form resolved. So posting a module's existing set and finding it intact is not a tautology: had resolution dropped the list, the unlink would still have run and the module would come back attached to nothing at all. The probe is `mod_online_users` — one of the three modules not in the protected-lid list that guards the seven powering the admin pages.
  - **Still on nids:** `page_nid` (48) and `text_nid` (4) — admin_pages and edit_texts, one release each.
  - **Verified:** `make check` exit 0 at 13 house rules; `make test` **113 PASS / 0 FAIL**; `make test-authz` green; `make render-check` byte-identical across all **40** baselines after recapture. The two moved files were diffed **in full, outside the harness**, and all 140 changed lines are `value=`/`href=`/`data-href=` substitutions with nothing else touched. The two new `admin_mods_edit` cases were captured twice, diffed, and read: `mod_online_users` addressed by lid, `level_admin` and its `admin` page both `selected`, no empty-valued control. `test/style.counts` re-banked — the model grew 2,325 → 2,347 lines for the new resolver, and `lines_over_120_columns` **fell** 360 → 357, because replacing `$_POST['modify_item_nid']` with a resolved local shortens the lines it appears in.

## [0.9.13-alpha] - 2026-08-14
- **CI went red on 0.9.12-alpha, and the cause was a sort that had never sorted anything. The levels list ordered its "groups" column by whatever order the rows happened to come back in — so a test that edited a group set and put it back reordered the page, and the render baselines disagreed with themselves.** The sort key was written as `luna:group[@rdf:about = @rdf:resource]/luna:lid` inside `<xsl:sort>`. In XPath the `@rdf:resource` in that predicate is read against the `luna:group` being *tested*, not the one being sorted — and a `luna:group` subject carries `@rdf:about`, never `@rdf:resource`. So the predicate was `@rdf:about = ''`, matched nothing, and every key evaluated to the empty string. Equal keys mean a stable sort, and a stable sort of unsorted input is document order. The fix is `current()/@rdf:resource`, which is the idiom the author plainly intended.
  - **This is the failure mode this project keeps finding, in a new place: a mechanism that runs, reports nothing wrong, and does nothing.** It is the same shape as house rule 13's fuzzy parser (0.9.6) and the `data-confirm` attribute nothing checked (0.8.66). A sort that cannot sort is indistinguishable from a sort that had nothing to reorder, which is exactly why it survived — the seeded order looked plausible, and the two sibling columns really were sorted.
  - **What made it visible was `test/lid_addressing.sh` L13**, added one release earlier, which grants a level a group and then takes it back. The set is restored exactly; the *row order* is not, because a delete-and-reinsert lands the rows the other way round. CI runs the suites before `render-check`, so the page rendered in the new row order against a baseline captured in the old one. **The baseline was the honest reporter here** — it was recording an ordering that nothing guaranteed, and the committed file proves it: one row read `Editors, Administrators` while another read `Anonymous, Administrators, Editors`, two different orders on one page.
  - **The two sibling sorts are fixed the same way, and their output does not move.** `pageslist`'s modules column and `groupslist`'s levels column both sorted correctly — but on `@rdf:resource`, which is the node URI, which is the nid. They now sort on the referenced node's `luna:lid` like the third. For the seeded data the two orders coincide, so nothing in those baselines changes; the point is that the ordering of a rendered list is no longer a function of the database's row ids, which is the same argument the whole `nid`→`lid` campaign rests on.
  - **Proved by forcing the condition rather than by reasoning about it.** The levels page was rendered with the map rows in the order the suite left them, then the rows were deleted and reinserted in the opposite order and it was rendered again: byte-identical, ordered `Administrators, Anonymous, Editors` both times. Then the exact CI sequence that failed — the full suite run, followed by `render-check` — was re-run here and comes back byte-identical.
  - **Verified:** `make check` exit 0 at 13 house rules with no ratchet movement; `make test` **106 PASS / 0 FAIL**; `make render-check` byte-identical across all 38 baselines after recapture, and byte-identical *again* after a full suite run. Six baselines moved, all of them the levels list's group column and every changed line inspected.

## [0.9.12-alpha] - 2026-08-14
- **admin_levels addresses levels and their admitted groups by lid. Three screens of six.** The mechanical half is now the established pattern — the list template, the modify form's hidden fields, the XPath keys, and the groups picker via `forminput`'s opt-in `option-key`. What is worth stating is the half that did *not* move.
  - **The access guard is the reason this screen is not merely a rename.** `submit_modify()` and `submit_delete()` both gate on `lunaAuthz::user_can_access_level(luna::$session->user, …)`, and that guard is what stops an administrator editing or deleting a level above their own. The two are belt and braces in the right order: resolution refuses what the requester cannot see, and the guard refuses what they can see but may not change. L13 therefore moves `level_edition`'s group set, reads it back out of `luna_nodes_map`, and restores it; the restore is rebuilt from the values read before the change rather than hard-coded, so the suite cannot drift the seed if the seed changes.
  - **Left alone, deliberately:** `add_level_groups` and `modify_level_groups` still inject `group_admin` by nid after resolution, because "any level must be accessible to administrators" is an invariant of the write path and not something the form is entitled to express. Resolving the posted list first and injecting afterwards keeps that ordering intact.
  - **Still on nids:** `page_nid` (48), `mod_nid` (40), `text_nid` (4) — admin_pages, admin_mods and edit_texts. `user_nid`, `group_nid` and `level_nid` appear nowhere in the rendered site.

It surfaced here only because converting admin_users moved that file a second time, and the second time there was a diff.

Every other type has asserted `luna:lid` since 0.9.3-alpha. Without it `get_node_from_slug()` — which matches on exactly that predicate — could not resolve a user at all, so the PHP half of this release would have failed for the same reason the checkbox did. **It discloses nothing new:** the same string is already on the same node as `foaf:mbox`, and no published surface carries Person nodes at all, which was checked rather than assumed — `?output=xml/n3/json/jsonld`, `/data/{slug}`, the sitemap and robots.txt contain zero user nodes and zero email addresses.

The per-target authz on group assignment likewise still runs over resolved group nids. `test/admin_lockout.sh` and `test/delegated_admin.sh` now post `user_lid=` and group lids, and both suites pass unchanged in what they assert.

L6/L6b/L7 cover the users list and its groups picker, L8 the modify form, and L9/L9b write a surname through the lid path and read it back out of `luna_users` before restoring it. ## [0.9.10-alpha] - 2026-08-14
- **0.9.9-alpha stopped publishing the database counter as an *identity*. It went on publishing it as an *address*: `?group_nid=4` in every link, `modify_item_nid` in every form, `<option value="7">` in every picker. The admin_groups screen now addresses every node by its slug, and this is the first of six — the rest follow one release at a time.** Nothing about the old links was wrong on the Semantic Web terms decision #4 was argued on; an address is not an identity claim. What is wrong with them is plainer: `luna_nodes.nid` is an autoincrement counter, so `?group_nid=4` cannot be written or read by a human, cannot be guessed, and does not survive a reseed — while `?group_lid=group_admin` does all three, and is the same string the store, the router and `/id/{slug}` already agree on.
  - **It is a boundary conversion, and that is the design rather than a shortcut.** The frontend emits and accepts lids; PHP resolves each one to a nid at the request boundary; everything below is untouched. `luna_nodes_map` still joins integers, `insert_action()` still takes a nid, and — the part that matters — `lunaAuthz::user_can_access_level()` still receives exactly the integer it always did. Converting the write paths as well would have meant re-proving the access control, and there was no reason to spend that risk on a change about what appears in a URL.
  - **Resolution goes through the ACL-scoped index, never the node table, and that single substitution is the whole security content of the release.** [`lunaModel::check_requested_node_by_lid()`](luna/luna.classes/luna.model.class.php) and [`nids_from_lids()`](luna/luna.classes/luna.model.class.php) both resolve through `get_node_from_slug()`, which scans the working index the requester's levels already scoped — so a lid the requester may not address resolves to false, exactly as a nid they may not address already did through `get_node()`. `get_nid_from_lid()` was the tempting helper here and is the wrong one: it queries `luna_nodes` at full scope and would have handed back a nid for a node the ACL had excluded, turning a rename into a privilege escalation.
  - **The escalation guard was re-proved to *fire*, not merely to hold.** `test/delegated_admin.sh` now posts lids, and it still asserts the *message* — "Access denied" — and not only that the grant is absent, because those two are different facts and only one of them survives a resolution that quietly drops the level. It survives for a reason worth writing down: `load_nodes()` applies its `nid IN (user->levels)` filter only to a **joined** type, never to its own, so `load_nodes('level')` loads every level regardless of what the requester holds. `level_admin` therefore resolves for a delegated admin exactly as its nid did, and `user_can_access_level()` is what refuses it. Had that load been scoped, the attempt would have been dropped at resolution and the suite would have failed on the message — which is why the message is asserted.
  - **A new suite, and it exists for the failure that looks like success.** [`test/lid_addressing.sh`](test/lid_addressing.sh) (`make test-lids`, in `make test` and CI) asserts the list links by lid and carries no surviving `?group_nid=`, the picker is keyed by lid, `?group_lid=` reaches the modify form — and then **writes through the lid path and reads the row back out of MySQL**. That last one is the point: a boundary conversion that resolves to nothing renders a completely correct page, so L1–L3 would all pass on a screen whose save silently does nothing. **Verified by breaking it deliberately:** made to return an empty array, `nids_from_lids()` leaves L1, L2, L3 and L5 passing and fails exactly L4 and L4b. The suite also reverts what it grants, because the render baselines are captured against the seeded level set.
  - **`forminput` is opt-in, because it is one template behind every select in the admin.** It emits the `<option value>` for all six screens, so converting it outright would have moved them all at once and made the release unreviewable. It gains an `option-key` parameter that still defaults to `nid`; admin_groups passes `lid`, and the last screen to convert will flip the default and delete the parameter. The internal `$option_nid` is renamed `$option_value`, and the three `schema:identifier = …` comparisons around it now compare `$option_value`, so the `required` and `default-value` callers are checked against whichever key the caller chose rather than against the integer regardless. **That the opt-in actually holds is asserted rather than assumed:** admin_pages, admin_mods, admin_users and edit_texts are byte-identical across this change.
  - **Two new render cases, because the list view cannot see most of what changed.** The hidden item field, the XPath keys that select the group being edited, the picker's selected state and the members table are reachable only with a `?group_lid=` in hand, so `admin_groups_edit` and `admin_groups_edit_fr` render the modify form. They point at `group_edition`, which is unpopulated in the seed — `delegated_admin.sh` puts a user in that group and takes them out again, so a baseline pinned to its membership would be ordering-dependent where this one is not.
  - **What is deliberately left on nids, and why it is not an oversight.** The group members' table links out to `admin_users?user_nid=`, and the shared online-users widget does the same; both belong to admin_users and convert with it. `$masternodenid` — defined in [`luna.header.html.xsl`](luna/luna.xsl/luna.html.xsl/luna.header.html.xsl) as a lid→nid→alias round-trip, since `$masternodelid` is right there — is shared by six stylesheets and emits no nid into any page, so it is a simplification for the cleanup release rather than part of this one. Both are now *visible in a committed baseline*, which is the difference between a deferral and a loose end.
  - **Verified:** `make check` exit 0 with all 13 house rules green; `make test` **93 PASS / 0 FAIL** across six suites (was 83 across five); `make test-authz` green; `make render-check` byte-identical across all **34** baselines after recapture, with two consecutive captures diffed to prove the two new cases deterministic, and the suites-then-render-check ordering CI uses re-run to confirm nothing is left behind. Four baselines moved and every changed line was read: `?group_nid=4` → `?group_lid=group_admin` and `<option value="7">` → `<option value="level_admin">`, with `level_public` still carrying `selected="selected"`, which is what proves the `required` comparison followed the key. A legitimate admin save was confirmed to reach the database and then reverted. `test/style.counts` re-banked for the model, which grew 2,247 → 2,318 lines — mostly the two docblocks, and recorded rather than hidden, since that ratchet exists to ask whether the class is still one thing. The one long line this change introduced was folded rather than banked.

## [0.9.9-alpha] - 2026-08-14
- **The same page was published under two URIs that never mentioned each other. Roadmap decision #4 is now resolved: the `/node/{nid}` route is retired, and `nid` is no longer an identity on any published surface — it survives as a non-identifying `schema:identifier` and as the loaders' internal key.** Asked one way, the home page was `<…/id/root>`, a `schema:WebPage` carrying `luna:lid`, `schema:name` and a `luna:level` pointing at `<…/id/level_public>`. Asked the other way, at `/node/9`, it was `<…/node/9>`, a `luna:page` carrying `luna:nid`, `rdfs:label` and a `luna:level` pointing at `<…/node/6>`. Same page, same access level, two names each, and **no `owl:sameAs` between them** — so a machine that read both documents had nothing to tell it that it had read one page twice.
  - **This is decision #9's defect one level up, which is why it is the same kind of deletion.** #9, closed in 0.9.3-alpha, was one predicate meaning two things depending on which surface you asked. This is one *resource* having two names depending on which surface you asked. On the Semantic Web the URI is the identity, so publishing two unlinked URIs for one thing does not read as untidiness — it asserts there are two things. The project's cardinal rule freezes `/id/{slug}`; it never adopted `/node/{nid}`, and nothing should have been minting it.
  - **The route published the model's internal shape, which `project_to_schema()` exists to translate away before anything is published.** `mod_node` predates the linked-data layer: it took the nid from the path, checked the requester's level, and emitted the raw nid-keyed index straight out of the working model — `luna:page`, `luna:nid`, `luna:alias`, and node-valued URIs pointing at further `/node/{nid}`. Every other output format goes through the schema.org/slug projection at the `transform()` boundary. This one went around it. The nid-keyed index itself is untouched and still correct: it is how the model is keyed in memory, and `docs/architecture.md` and `docs/linked-data.md` describe it accurately. What is retired is publishing it.
  - **It was hidden from humans and advertised to machines, and that combination is the part worth keeping.** `luna.common.html.xsl` carried a hardcoded `not(luna:lid = 'node')` in both its `sitemap` and `recursesitemap` templates — someone had already decided the page should not appear in the site navigation. Meanwhile `/sitemap.xml`, the crawler-discovery endpoint of the publishing surface, listed `http://localhost:8080/node`; and bare `/node` returns **HTTP 200 with a zero-byte body**, because `mod_node` needs a nid from the path and `die()`s on the missing subdir. So of the two URLs the public sitemap offered a crawler, one was the site root and the other rendered nothing — the same 200-with-an-empty-body signature closed in 0.9.8-alpha, this time posted to machines deliberately. The seed page is gone, the sitemap is down to one URL, and **both stylesheet exclusions are deleted**: retiring the route removes a special case rather than adding one.
  - **What this costs, stated rather than absorbed.** `/node/{nid}` was the only route that served a *non-page* node as RDF — a level, a group, a user, a text. `/id/{slug}` and `/data/{slug}` cover pages only, so those resources now have no RDF representation at all. That does not create a gap so much as consolidate one already recorded on P4 ("dereference text/`Article` resources too"), and the replacement belongs there, in the slug vocabulary, rather than in a route keyed by a database counter. It is a real subtraction in the meantime.
  - **Existing databases need two `DELETE`s, and the failure without them is bounded but not silent.** `load_mods()` scopes its query to the current page (`pm.nid1 = PAGENID`), so a stale `mod_node` row breaks only the `node` page and not the site; visiting it throws "cannot find mod file mod_node" at `PEAR_LOG_CRIT`. With the nav exclusion gone the page also reappears in the site map, which is the honest outcome — it is a real page in that database. Remove it with `DELETE FROM luna_nodes_map WHERE nid1 IN (31,32) OR nid2 IN (31,32); DELETE FROM luna_actions WHERE nid IN (31,32); DELETE FROM luna_nodes WHERE nid IN (31,32);`, or reseed. `luna_nodes_seq` deliberately stays at 33: it records the last value allocated, not the row count, and the gaps it now leaves are harmless for exactly the reason this release exists.
  - **The catalogues are deliberately untouched.** `node` remains a msgid in both locales, translated ("Node" / "Nœud"), and it *was* being consumed — a page's display name is its slug run through gettext, which is why the removed rows show as `Nœud` in the French baselines. With the page gone the entry is dead, but it is a common noun any future page or vocabulary key could claim, and removing it means recompiling both binary artifacts to satisfy house rule 13. A dead msgid costs nothing at runtime. A dead *registration* does cost something — it is a lid the tree claims and no stylesheet consumes — so the `'node'` entry in `transform()`'s `add_vocabulary()` list is removed here, along with `mod_node`'s own.
  - **Verified:** 7 of the 32 render baselines moved and **every changed line was read before the recapture** — all of them removals of nid 31 (`mod_node`) or nid 32 (`node`) from a list, a table or a picker, plus the four `<select size="N">` counts that follow arithmetically; zero additions, zero unrelated changes, and the other 25 baselines byte-identical. Two consecutive captures diffed clean. `make check` exit 0 with all 13 house rules green and the module contract at 56 checks; `make test` **83 PASS / 0 FAIL** across the five suites; `make test-authz` green. The edited seed was loaded into a scratch database from cold and checked for referential damage: 31 nodes, 94 map rows, 31 action rows, and zero dangling map rows, actions or parent pointers. `/node`, `/node/9` and `/node/10` all confirmed 404 over HTTP, where `/node/9` and `/node/10` were 200 before. Both ratchets fell with the deleted file (`functions_without_return_type` 116 → 114, `lines_over_120_columns` 363 → 360) and were re-banked.

## [0.9.8-alpha] - 2026-08-14
- **Any visitor could blank any page with one character in a query parameter name, unauthenticated, and nothing in the stack registered it as a failure.** `GET /?a"b=1` returned **HTTP 200 with a zero-byte body**. So did `/login`, and so did `/admin` for a logged-in administrator. No credentials, no session, one character — and the affected surface is every page the XSLT transform renders, which is the entire human-facing site.
  - **The mechanism, and why it reached so far.** `lunaModel::load_request()` walks `$_REQUEST` and hands every parameter **name** to `lunaTools::prepare_var_key()`, whose result becomes the render-model bnode id and is then interpolated into `rdf:nodeID="…"` when the model is serialised for the transform. `squash_to_key()` maps whitespace and apostrophes but passed `"`, `<` and `&` through untouched: a double quote closes the attribute, `<` and `&` are illegal in that position outright. The document stops being well-formed, the transform yields nothing, and PHP has already sent `200`. The character set is exactly predictable from the mechanism and was confirmed against it — `"`, `<` and `&` blank the page; `>` does not, because it is legal unescaped in an attribute value, and `'` does not, because `squash_to_key()` already maps it to `-`.
  - **The fix is an allowlist, applied in `prepare_var_key()` and deliberately not in `squash_to_key()`.** Restricting the output to `[A-Za-z0-9_-]` is safe by construction rather than by enumeration — blocking the three characters known to break XML today would leave the next serialisation context to be found the same way. It is **not** applied to the shared helper, because `prepare_lid()` uses that too, and `prepare_lid()` feeds `luna_nodes.lid`, which is frozen resource identity under this project's cardinal rule. This narrows what a render key may contain and changes nothing a slug may contain. The method's own docblock already claimed this guarantee — "these keys become `rdf:nodeID` values when the render model is serialised for the transform" — so this is the method being made to keep a promise it had already documented.
  - **Why no gate saw it, which is the part worth keeping.** The failure *is* an HTTP 200, so every status-code check passes vacuously — the same trap `test/regression.sh` already warned about for `/node`. The access log records `200 1110` for a zero-byte response, because that is the header size, so byte-count monitoring reads healthy too. And `?output=xml`, `?output=jsonld`, `/sitemap.xml` and `/robots.txt` are all immune, since `ui:request` bnodes are serialised nowhere but the transform — so any check aimed at the RDF surfaces confirms the site is fine while every page it serves is empty. A 200 with an empty body is worse than a 500 here: caches store it, and nothing treats it as an error.

So when 0.8.34-alpha purged the dead `lunarsystem.org` domain it changed both `.po` headers and nothing else, and `Last-Translator: Odradek <odradek@lunarsystem.org>` went on shipping to every visitor inside the binary. Both catalogues are recompiled here, and the drift is now a rule rather than an observation.
  - **Recompiling was proved lossless before it was done, because it is the one step that could have destroyed translations.** A source that has fallen *behind* its artifact is the dangerous direction: `msgfmt` writes only what the `.po` carries, and silently drops fuzzy and untranslated entries besides. Neither applied. Decompiling both artifacts gave identical msgid sets in both directions, an identical `msgstr` for every pair, and zero fuzzy, untranslated or obsolete entries in either source — so nothing existed in the binary that the source could not reproduce. The proof was run against the sources untouched, before the key cleanup described below: recompiled from the `.po` exactly as it then stood, each artifact came out exactly 26 bytes smaller than its committed counterpart — the length of ` <odradek@lunarsystem.org>`, and at that point the whole of the difference. **That figure measures the header fix alone and does not describe this commit's diff**, in which the artifacts grow because the key cleanup below rewrites 32 msgids into a three-byte-per-quote form: en_US goes 17112 → 17336 bytes, fr_FR 18225 → 18160.
  - **It survived because the artifact is binary and the search that would have found it cannot read binaries.** `git grep -I` skips binary files silently — as does BSD `grep` without `-a` — so a text sweep of the tree reported clean while the string sat in two committed files. Plain `git grep -l` does find it. The two mechanisms are different, and reproducing with the wrong one makes the finding look false, which is why both are named here. The general shape is worth more than the instance: a search that cannot read the file it is searching returns "clean" and "absent" as the same answer.
  - **New house rule 13 holds a catalogue to its source, by content, including the header.** mtime is not the test — git does not record it, so on a fresh clone or in CI every file carries checkout time and an "is the `.mo` newer than its `.po`" check would pass vacuously in the one place it most needs to hold. The rule reads the `.mo` binary directly with `unpack()` and takes no `msgfmt` dependency: `make check` runs in `php:8.3-cli`, where the gettext CLI does not exist, while CI runs on `ubuntu-latest`, where it does — and a gate that resolves through different machinery in its two environments is not one gate. It compares the header too, which is the whole point: this drift lived *entirely* in the header, every msgid/msgstr pair agreed, and a check over pairs alone would have passed on the stale file and reported nothing. Verified by watching it fail — pointed at the two files exactly as they shipped, it names the header and nothing else. One concession: `msgfmt` canonicalises the charset spelling (`utf-8` → `UTF-8`), so that single value is case-folded and the rest of the header compared exactly.
  - **The two locales disagreed about their own keys, and the tractable half of that is fixed here.** en_US and fr_FR shared only 256 msgids. Thirty-two pairs were the same message under two quoting conventions — en_US wrote `'%1$s'` where fr_FR, and *every call site in the source*, writes `“%1$s”` — so those thirty-two en_US entries were dead keys gettext could never reach. Nothing looked wrong because all thirty-two were identity translations that fell through to the same English, which is exactly why it went unnoticed for so long. en_US now uses the curly form the source actually calls. `rootMod` (en_US) and `root_mod` (fr_FR) are dropped as vestigial: the live key is `root_module` and both catalogues already carried it correctly. `levels` is added to en_US, which lacked it entirely. The two sets are now identical at 289 msgids.
  - **Found, not fixed, and recorded so it is not lost:** of the 160 live `lunaTools::add_vocabulary()` lids, 16 have no entry in either catalogue and fall back to the raw literal — so the French interface renders "Delete from the level" and the Markdown editor hint in English, and both locales show bare keys such as `cache_timeout` and `identifier` where a label belongs. That is translation coverage rather than drift, and it belongs to its own change.
  - **Correction to the 0.9.0-alpha entry above:** it dates the dead address to 0.3.6-alpha. That release added `docs/why-rdf.md` and touched nothing else. The `lunarsystem.org` *production domain* went in 0.4.0-alpha; the `odradek@` address in the `.po` headers went in 0.8.34-alpha. The entry is left as written, since it is the record of what was believed at the time.

## [0.8.67-alpha] - 2026-08-14
- **Multilingual content was a paper feature that destroyed content when used as documented. Saving a translation rewrote every other language of that text, the reader never consulted the visitor's language at all, and the graph carried exactly one translation chosen by accident. All three are fixed, and the invariant they all violated is now a database constraint rather than an intention.** Four defects, and they compound: the schema said the wrong thing, so every layer above it was free to be wrong in its own way.
  - **The schema never stated its own design.** `luna_texts` was built one row per (node, language) — the column exists, the editor posts it, the projection reads it — but the only key was on `nid`, and `lang` was nullable. Nothing prevented duplicates and nothing tied a row to a language. It now carries `UNIQUE KEY nid_lang (nid, lang)` with `lang NOT NULL`; `NOT NULL` is load-bearing rather than tidiness, because MySQL permits unlimited `NULL`s inside a `UNIQUE` index and a nullable column would have left the same hole open. `KEY nid` is gone as the leftmost prefix of the new key, not as a loss.
  - **Editing one language destroyed the others.** [`mod_edit_texts::submit_modify()`](luna/luna.mods/luna.mod_edit_texts.php) ran `UPDATE … SET title, lang, content WHERE nid = ?` — no language predicate — so saving the French text rewrote the English row to *be* French, silently, with no way back. Both the add and modify paths are now upserts keyed on `(nid, lang)`. That also makes the language selector mean something for the first time: saving under a language that has no row creates that translation, saving under one that exists updates it, so "add a translation" needs no new form and no second code path.
  - **The reader ignored the requested language.** `lunaModel::load_texts()` selected `lang` and never filtered on it, then filed every row under `nid` — so the last row the database happened to return became the page's text, and the language selector, which has always driven interface strings and page labels, had never once reached content. Resolution is now deliberate and shared: `lunaTools::preferred_content_languages()` defines one ladder (the requested language, then the site's configured order), the SQL and SPARQL read paths both resolve through it, and a translation outside the ladder is still served rather than dropped, because a missing translation is a gap in the content and not a reason to render an empty page.
  - **A comparison that could never be true, and had never been true.** The RDF projection tried to prefer the request language with `$row->lang == luna::$lang` — but `luna::$lang` is the interface locale `"en-US"` (that is what `format_language()` produces) while the column is `char(2)` holding `"en"`. The test never matched, so the projection always took the first row it fetched. There are two language vocabularies in this system, and `lunaTools::content_language()` is now the only sanctioned bridge between them.
  - **The graph stopped being a lossy mirror.** Every translation is projected onto the same subject as a **language-tagged literal** — `schema:headline "Welcome"@en, "Bienvenue"@fr` — which is the mechanism RDF has always had for this and which the CMS was working around with a single untagged literal plus a `schema:inLanguage` annotation beside it. `schema:inLanguage` is still emitted, because the R2RML mapping and the existing read path look for it, but the tag is what the read path trusts now: a tag travels attached to the value it labels, an annotation does not. Anything querying these must correlate the tags — a text carries a headline *and* a body *and* a `luna:content` per language, so an uncorrelated join returns the cross-product and can pair an English headline with a French body; `load_texts_sparql()` filters on `lang(?title) = lang(?body)` for exactly that reason.
  - **Existing databases have a migration, and it is honest about what it is.** [`bin/migrate-texts.php`](bin/migrate-texts.php) (`make migrate-texts` to report, `make migrate-texts-apply` to write) normalises blank languages, collapses duplicate pairs keeping the newest row, and adds the key — idempotent, dry-run by default, and it names the rows it would delete before deleting them. It is a one-off repair for one table and **not** a migration framework; the project still has none, and pretending otherwise would be worse than saying so.
  - **A new suite, and it was checked against the defect it exists for.** [`test/multilingual.sh`](test/multilingual.sh) (`make test-multilingual`, and in `make test` and CI) asserts that two translations coexist, that editing one leaves the other untouched, that re-saving updates in place rather than duplicating, that `?lang=` reaches content, that a missing translation falls back instead of rendering nothing, and that the graph holds both headlines tagged `@en` and `@fr`. Run against the previous write path it fails four of those and reports the English row destroyed — the seed ships a single English row, which is precisely why every one of these defects survived: with one translation, a write path that clobbers all languages and a read path that ignores the requested one both look correct.
  - **Verified before promoting:** `php -l` clean on PHP 8.3; `make check` green at 7 house rules; the smoke/security-regression, delegated-admin, admin-lockout and multilingual suites green; all 21 render-baseline pages byte-identical (the change is output-neutral on single-language content, which is what it should be); the schema re-checked by loading `luna.mysql.sql` into a scratch database from cold; and the migration re-run to confirm it reports "nothing to do" the second time. `test/style.counts` re-banked: the model grew 42 lines and `luna.tools.class.php` crossed 1,000 lines for the first time — recorded rather than hidden, since that threshold is the ratchet's way of asking whether a class is still one thing.

Braces stay on the same line because the tree is unanimous and moving them costs a fifth of the line count to fix nothing. Method and class names keep their casing because `load_mods()` resolves module classes out of the database `lid` column, so renaming them is a schema migration wearing a style change's clothes. PSR-12 rather than PER Coding Style deliberately: PER is at 3.0 having passed through 2.0 quickly, php-cs-fixer already marks the `@PER-CS2.0` identifier deprecated, and a frozen spec is worth more than a current one for an artifact read far more often than edited.

Three calls passing an argument to a zero-parameter function; one passing two arguments to a one-parameter signature on the 404 route. `print_r($msg, 1)` where the parameter is a bool, and `load_nodes(0, …)` where the "no filter" sentinel is `false`.

## [0.3.4-alpha] - 2026-06-19
- Semantic web (P2, first step — URI-identity policy). Resolved roadmap decision #1 as **"forbid slug edits"** and enforced it: `lunaModel::update()` now refuses any change to a node's `lid`, since `<base/id/{lid}>` *is* the resource's identity and the cardinal rule is "freeze the URIs." ## [0.3.3-alpha] - 2026-06-19
- Semantic web (Phase C complete — the triplestore is now authoritative for the read/write loop; MySQL stays the system of record). The RDF track is being finished; the client-side-XSLT idea (roadmap P5) has been **dropped**. See [docs/linked-data.md](docs/linked-data.md) and [docs/roadmap.md](docs/roadmap.md).
  - **P0 — generic write-through.** Replaced the per-mod `rdf_put_article` hook with a generic projection wired into the model's CRUD, so *every* content write mirrors to the graph by construction:
    - `lunaModel::rdf_sync_node($nid)` re-projects a node's whole description (`DELETE { <uri> ?p ?o } INSERT { … }`) to match the R2RML mapping — typing the resource (`page`→`schema:WebPage`, `text`→`schema:Article`, `user`→`foaf:Person`, level/group/mod→`luna:`) and its edges (`schema:isPartOf`/`hasPart`, `luna:level`), with numeric values typed `xsd:integer`. Called from `insert`/`update`/`link`/`unlink` (and by `mod_edit_texts` after a text-body write).
    - `lunaModel::rdf_delete_node($nid)` removes every triple mentioning a resource (subject *and* object), inside `delete()`.
    - `lunaModel::rdf_resync_all()` re-projects every node from MySQL — a pure-PHP bootstrap/repair of the store that replaces the Ontop "materialise" step. Used to close a real drift gap (a page that predated the dual-write) to exact count parity.

Both the routing and text loaders keep an automatic **SQL fallback**; `?sparql=0` forces the SQL path. (`sanitize_inputs()` turns `'0'`→`false`, so the opt-out is read from `$_GET` with a `(bool)` cast, not via `lunaTools::request()`.)
  - Verified end-to-end on Docker: insert→link→delete of a throwaway page produced then fully removed its projection in Oxigraph; an Oxigraph-only sentinel rendered by default and vanished under `?sparql=0`; guest/admin routing + level-based ACL resolve from the graph.
  - Still SQL-only (by design, for now): the mod list (`load_mods`) and the `luna_actions` audit trail. Retiring the MySQL content write (single source of truth) is **P2**, blocked on the rename/URI-identity decision.
